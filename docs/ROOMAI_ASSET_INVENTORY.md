# ROOMAI 3D Asset Inventory

**Phase:** 4 — 3D Asset Production planning  
**Status:** inventory and specifications only. No production assets have been created or approved.  
**Scope:** first-party RoomAI immersive showcase; this document does not authorize changes to the FastAPI backend or construction of the website.

**Read-only workspace scan:** `artifacts/final_backend_verification/` currently contains `reconstructed_scene.glb` (482,132 bytes) and `reconstructed_pointcloud.ply` (1,352,478 bytes), along with evaluation/visualization outputs. `artifacts/uploads/` contains three uploaded image files. The scan did not establish which image pairs with that GLB/PLY, whether a matching metric depth map is available, or whether the image has public display rights. These are candidate inputs only, not an approved exhibit. A 47 MB scene-graph JSON output is not a browser asset and should not be copied into the runtime bundle.

## 1. Production principles

1. The hero room must be the **same real RoomAI reconstruction** used to make the product claim. The source RGB, depth, point data, and GLB must share traceable provenance and coordinate conventions.
2. One excellent exhibit scene is the priority. Do not model a fake furnished room, invent semantics, or substitute AI/stock imagery for reconstruction output.
3. `REALITY`, `DEPTH`, `POINTS`, `GEOMETRY`, and `HYBRID` are data representations. Only include a mode if the selected artifact contains what that mode requires.
4. Most lighting, atmosphere, camera, measurement graphics, point appearance, and transitions are **runtime code**, not files to author in a 3D package.
5. Evidence thumbnails and metric overlays are tied to the verified evaluation set and must preserve scene identity and provenance.

## 2. Asset class legend

- **Custom 3D assets:** actual RoomAI outputs or purpose-made Blender assets/proxies. “Custom” does not imply artist-made reconstruction geometry.
- **Procedural assets:** architectural staging primitives or diagrams generated by a deterministic Three.js/Blender script.
- **Downloadable assets:** licensed tools, fonts, or audio acquired with redistribution rights documented. No generic stock room models are planned.
- **AI-generated visual assets:** no AI-generated image is approved for the hero, reconstruction, evidence, or future capability examples. Optional private moodboard explorations are non-shipping and must not be mistaken for product output.
- **Code-generated effects:** shader/BufferGeometry and DOM/SVG effects built at runtime from real inputs.

## 4. Downloadable and AI-generated assets

### Downloadable

- **Fonts:** only when license permits web embedding and local hosting. Record foundry, license URL, allowed weights, and attribution requirement in a license ledger.
- **Audio:** optional only; prefer a commissioned/synthesized short tonal cue. Any downloaded sound needs redistribution rights and attribution terms recorded. No third-party room model, HDRI, stock photograph, particle pack, or paid Spline asset is required.
- **Tools/decoders:** Blender, glTF-Transform, and compression decoders are pipeline tools, not scene content. Pin versions in production notes and validate runtime licenses.

### AI-generated visual assets

**Shipping AI-generated visual asset count: 0.** The hero image, depth, point cloud, room, and evidence are product evidence and must come from the real input/inference/evaluation pipeline. Abstract Future diagrams are better made procedurally because they are precise and status-labeled. AI image generation may be used privately for composition moodboards only; never commit them into the final asset directories or present them as product output.

## 5. Asset priority for first playable prototype

### P0 — First playable, required

- A01–A04: one approved RGB/depth/point/GLB exhibit bundle (inspect actual GLB before confirming geometry modes).
- A06: manifest with provenance, axis/unit, bounds, reset framing, supported representations, and PRECOMPUTED truth label.
- A10–A11: photo plane and scroll-driven depth surface.
- A14–A16: point rendering, a usable LOD, and camera crossing rail.
- A17: restrained representation/material reveal.
- A19: verified room presentation from actual output.
- A22: basic selection feedback only if feasible; can be P1 if point-only export lacks stable hit semantics.
- A33: consistent color values/tokens.

First playable definition: dark room → recognizable RGB photograph → aligned depth separation → data-derived point cloud → controlled camera crossing → stable real reconstructed room → orbit/pan/zoom/reset. A pre-rendered sequence can cover low-capability devices, but the desktop first-playable must demonstrate the actual reconstruction live in the browser.

### P1 — Complete planned experience after the core path works

- A07–A09 room staging and lighting; A13 depth marker; A20 low-detail fallback; A21 pipeline visuals; A22 selection marker; A23 measurement tool; A24–A25 evidence; A26 limitations treatment; A27–A30 Future diagrams; A31 project still; A32 mobile fallback; A34 font families; A35 guide-line system.

### P2 — Optional polish

- A12 interactive contours; A18 sound; A36 any postprocessing beyond the core WebGL material transitions. No P2 item should delay the real room, point field, or camera work.

## 6. Not production assets / explicit exclusions

- No custom furnished room model built to resemble the source photograph.
- No random dust, starfield, unrelated particles, AI brain, neon, bloom, or generic futuristic stock art.
- No invented object labels, coordinates, measurements, or 3D Gaussian asset.
- No multi-view/CAD/scene-graph render represented as current product output.
- No full copy, metrics, navigation, or ordinary interface text baked into textures or meshes.
- No backend modification and no shipping of the entire `artifacts/jobs` tree.

## 7. Asset acceptance record

Before each asset enters `04-runtime`, record: owner/source, license, checksum, source artifact ID, transformation history, axis/units, format, dimensions/sample count/triangles, supported modes, device tier, optimization settings, and visual QA result. Runtime exports are derived and replaceable; source outputs remain unchanged.
